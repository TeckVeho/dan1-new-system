## 2. 認証設計

### 2.1 ログイン方式

FR-101, FR-103。

| ユーザー種別 | ログインID | 備考 |
|------------|-----------|------|
| 社内ユーザー | 社員番号（例: `100002`） | 主ID |
| 社内ユーザー（別名） | **HACCP番号**（例: `00020`） | 現場の認識に合わせる（A-02 の解消） |
| 社内ユーザー（別名） | メールアドレス | 任意 |
| 施設ユーザー | 施設コード（例: `10234`）またはメールアドレス | `[要確認]` 施設内で複数アカウントを発行するか |

ログイン画面ではユーザー種別を選択させず、入力されたIDから自動判別する。社員番号・HACCP番号・施設コードが衝突しない前提だが、実装時は種別ごとにテーブルを分けて順に照合する（`users` → `customer_users`）。

### 2.2 パスワード

NFR-10-1, NFR-10-2。

| 項目 | 仕様 |
|------|------|
| ハッシュ | Argon2id（メモリ64MB / 反復3 / 並列度4） |
| 最小長 | 12文字 |
| 文字種 | 英大文字・英小文字・数字・記号のうち3種以上 |
| 禁止 | ログインIDと同一、ログインIDを含む、氏名を含む、既知の流出パスワード（`[要確認]` 外部APIを使うか） |
| 初回変更 | `password_changed_at` が NULL の場合は変更を強制 |
| 有効期限 | 設けない（定期変更の強制は推奨されないため） |
| 履歴 | 直近3世代の再利用を禁止 `[要確認]` |

**移行時の対応。** 現行は全ユーザーのパスワードがログインIDと同一のため、移行時に初期パスワードを個別発行し、初回ログインで変更を強制する（`12_migration_plan.md`）。

### 2.3 多要素認証

FR-102。

| ロール | MFA |
|--------|-----|
| システム管理者 | **必須** |
| 社内管理者 | **必須** |
| 社内一般 | 推奨（任意で有効化） |
| 施設管理者 / 施設一般 | 任意 |

方式は TOTP（Google Authenticator 等）。リカバリーコードを10個発行する。

社内管理者に必須とする理由は、マスタ変更・請求訂正・成り代わりといった影響の大きい操作が可能なためである。

### 2.4 セッション

NFR-10-5。

| 項目 | 仕様 |
|------|------|
| 方式 | サーバーサイドセッション（Cloud Memorystore for Redis または Cloud SQL） |
| Cookie 属性 | `HttpOnly` / `Secure` / `SameSite=Lax` / `Path=/` |
| 有効期間 | 社内8時間 / 施設24時間 `[要確認]` |
| アイドルタイムアウト | 社内2時間 / 施設8時間 `[要確認]` |
| 同時セッション | 制限しない。ただしユーザーが自分のセッション一覧を確認・失効できる |
| 失効 | ログアウト、パスワード変更、ロール変更時に全セッションを失効 |

JWT ではなくサーバーサイドセッションを選ぶ理由は、ロール変更・成り代わり・強制ログアウトを即座に反映する必要があるためである。

### 2.5 アカウントロック

| 条件 | 動作 |
|------|------|
| ログイン失敗5回 | 15分間ロック（`locked_until`） |
| ロック中の試行 | 失敗としてカウントせず、残り時間を表示 |
| 管理者による解除 | ユーザー管理画面から即時解除可 |
| 通知 | ロック発生時に本人（メール登録がある場合）と社内管理者へ通知 |

## 4. スコープ制御

### 4.1 施設スコープ

NFR-10-7。施設ユーザーは自施設のデータのみアクセスできる。

**実装方針**

リポジトリ層でクエリ条件を強制注入する。コントローラ層の実装漏れによる情報漏洩を防ぐため、コントローラでの条件付与に依存しない。

```typescript
// packages/database/src/repositories/base.ts
function applyCustomerScope(where: object, ctx: RequestContext) {
  if (ctx.userType === 'facility') {
    return { ...where, customerId: ctx.customerId };
  }
  if (ctx.impersonatingCustomerId) {
    return { ...where, customerId: ctx.impersonatingCustomerId };
  }
  return where;
}
```

**検証項目**（NFR-10-7 のセキュリティテスト）

| 攻撃パターン | 期待結果 |
|------------|---------|
| URL のIDを他施設のものに書き換える | 403 `SCOPE_VIOLATION` |
| API のリクエストボディに他施設のIDを含める | 403 |
| 一覧APIで他施設のデータが混入する | 混入しない |
| ファイルのダウンロードURLを推測する | 署名付きURLのため不可 |

### 4.2 業者スコープ

社内一般ユーザーの操作可能業者を `user_supplier_scopes` で制限する。

| 状態 | 動作 |
|------|------|
| レコードが存在しない | 全業者を操作可能 |
| レコードが存在する | 該当業者のみ操作可能 |

現行との違いは、**排他ロックではなく権限範囲**である点。複数ユーザーが同一業者を同時に閲覧・編集できる。

## 5. 成り代わり（インパーソネーション）

REQ-03 に対応。FR-105。

### 5.1 目的

要望原文「各施設様のサイトを閲覧および編集できるように改善してほしい ※請求書発行後に、各施設様に請求書が正しく発行されているか確認できること」に対応する。加えて、電話注文の代理入力にも使える。

### 5.2 仕様

| 項目 | 仕様 |
|------|------|
| 権限 | `admin.impersonate`（システム管理者・社内管理者） |
| 開始 | 施設一覧または施設編集画面から「施設ビューで確認」 |
| モード | 閲覧のみ / 操作可 を開始時に選択 |
| 表示 | 画面上部に固定バーを常時表示（`○○苑 として表示中 [終了]`） |
| セッション | 元のセッションを保持し、成り代わり情報を追加する（別ログインではない） |
| 有効期間 | 30分でタイムアウト。延長可 `[要確認]` |
| 終了 | バーの「終了」または自動タイムアウト |

### 5.3 監査

すべての操作を監査ログに記録する（FR-001）。

| 記録項目 | 内容 |
|---------|------|
| `actor_type` | `internal` |
| `actor_id` | 実操作者（社内ユーザー）のID |
| `impersonated_customer_id` | 成り代わり対象の施設ID |
| `action` | 通常の操作種別（`create` / `update` 等）。開始・終了は `impersonate` |

「誰が」「どの施設として」「何をしたか」が追跡できる。成り代わり中の注文登録は `meal_orders.ordered_by_type = 'internal'` として記録され、施設自身の入力と区別できる。

### 5.4 制限

| 制限 | 理由 |
|------|------|
| パスワード変更は不可 | 施設ユーザーの認証情報を社内が変更できるべきでない |
| 施設ユーザーの追加・削除は不可 | 施設管理者本人の操作とすべき |
| 成り代わり中の成り代わりは不可 | 追跡が複雑になる |

## 6. 排他制御

REQ-22 に対応。FR-307。**現行の業者ロックを廃止する。**

### 6.1 方針の変更

| 観点 | 現行（悲観ロック） | 新システム（楽観ロック） |
|------|------------------|----------------------|
| 取得タイミング | ログイン直後に業者を選択 | なし |
| 粒度 | 仕入業者（119商品×全納品日） | レコード（1商品×1納品日） |
| 他ユーザーの操作 | 完全に禁止 | 可能。競合時のみ検出 |
| ロックの解放 | 明示操作または管理者の強制解除 | 不要 |
| 離席時の影響 | 他ユーザーが作業できない | 影響なし |

### 6.2 楽観ロックの実装

すべてのトランザクションテーブルに `version` カラムを持たせる（`05_data_model.md` §1.2）。

```sql
UPDATE order_schedules
SET order_qty = ?, version = version + 1, updated_at = NOW(3), updated_by = ?
WHERE id = ? AND version = ?;
-- 更新件数が 0 なら競合
```

Prisma では `updateMany` の戻り値 `count` で判定する。

### 6.3 競合時のユーザー体験

競合は排除すべきエラーではなく、通常起こりうる事象として扱う。

```
1. ユーザーAとBが同じセルを開いている
2. Aが発注数を 31.000 → 35.000 に変更して保存（version 5 → 6）
3. Bが 31.000 → 33.000 に変更して保存を試みる（version 5 を送信）
4. サーバーが 409 VERSION_CONFLICT を返す
   - 現在値: 35.000
   - 更新者: 和田 洋宗
   - 更新日時: 2026-08-04 10:15
5. Bの画面に差分が表示され、選択肢を提示
   [相手の値を採用（33.000を破棄）] [自分の値で上書き（35.000→33.000）] [キャンセル]
```

現行の悲観ロックでは、Bはそもそも画面を開けなかった。新方式では作業でき、衝突した場合のみ判断を求められる。

### 6.4 編集中インジケータ

競合の発生確率を下げるため、他ユーザーが同一レコードを開いていることを表示する（ロックはしない）。

| 項目 | 仕様 |
|------|------|
| 記録 | `record_locks` テーブル（`entity_type` / `entity_id` / `user_id` / `expires_at`） |
| 取得 | 編集画面を開いた時に登録 |
| 維持 | 30秒間隔のハートビートで `expires_at` を延長（既定5分） |
| 表示 | 行またはセルに `近藤 志保 が編集中` を表示 |
| 解放 | 画面を離れた時、または有効期限切れ（定期ジョブで削除） |
| 強制力 | **なし。** 表示のみで編集は禁止しない |

テーブル名が `record_locks` だが実際にはロックしない。この点は実装時に誤解されやすいため、コード上のコメントとレビューで明示する。

### 6.5 一括処理の排他

同時実行すると不整合が生じる処理には、ジョブレベルの排他を設ける。

| 処理 | 排他方式 |
|------|---------|
| 発注量の再計算（同一業者・同一期間） | `jobs` の `job_type` + `params_hash` + `status` で重複を検出し 409 |
| 請求締め処理（同一施設・同一月） | 同上 |
| データ取込（同一ファイル） | `file_hash` で重複を検出 |
| 月次パーティション追加 | Cloud Scheduler の単一実行 |

## 7. 権限検証の実装

|----|---------|------|
| フロントエンド | メニュー・ボタンの表示制御 | UX。セキュリティ境界としては信頼しない |
| API ミドルウェア | ロールの権限保有チェック | 主たる検証（NFR-10-6） |
| リポジトリ層 | 施設・業者スコープの強制注入 | 実装漏れの防止（NFR-10-7） |

### 7.2 ミドルウェアの例

```typescript
// apps/api/src/middleware/authorize.ts
export function authorize(...required: PermissionCode[]) {
  return (req: Request, res: Response, next: NextFunction) => {
    const granted = req.context.permissions;
    const missing = required.filter((p) => !granted.has(p));
    if (missing.length > 0) {
      return next(new ForbiddenError('この操作を行う権限がありません', { missing }));
    }
    next();
  };
}

// 使用例
router.patch(
  '/procurement/schedules/:id',
  authenticate,
  authorize('procurement.schedule.update'),
  supplierScopeGuard,
  updateSchedule
);
```

### 7.3 特権操作の追加要件

以下の操作は権限保有に加えて追加の条件を課す（NFR-10-8）。

| 操作 | 追加要件 |

| `order.update_after_deadline` | 理由の入力を必須とし監査ログに記録 |
| `invoice.correct` | 訂正理由の入力を必須 |
| `admin.impersonate` | 開始・終了を監査ログに記録。画面に警告バーを常時表示 |

| `admin.role.update` | 変更後に対象ユーザーの全セッションを失効 |
