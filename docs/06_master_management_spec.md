# 06. マスタ管理仕様（設定駆動）

作成日: 2026-08-04

本ドキュメントは REQ-02「マスタでできないことが多いのでやりたい」への回答である。クライアント要望24件のうち7件（REQ-02, 08, 09, 10, 11, 12, 13）がマスタの制約に起因しており、本仕様の達成が本プロジェクトの中心的な成功条件になる。

---

## 1. 設計原則

### 1.1 開発者依頼ゼロの原則

業務担当者が画面から完結できるべき操作を定義し、これらにコード変更を要求しない。

| 操作 | 現行 | 新システム | 対応REQ |
|------|------|----------|---------|
| 締切時刻の変更 | 開発者依頼（加藤氏） | 締切ルールマスタ | REQ-13 |
| 正月の締切前倒し | 開発者依頼 | 締切例外日マスタ | REQ-13 |
| 嚥下食区分の追加 | 開発者依頼 | 嚥下食区分マスタへの行追加 | REQ-09 |
| 嚥下食の並び順変更 | 開発者依頼 | 表示順のドラッグ操作 | REQ-07 |
| 集荷日・着日パターンの変更 | 開発者依頼 | 製造パターンマスタ | REQ-08 |
| 食種変更に伴う資料出力の切替 | 開発者依頼 | 資料出力ルールマスタ | REQ-11 |
| 誤登録アレルギーの削除 | 不可 | 施設別アレルギー設定の論理削除 | REQ-12 |
| 施設登録内容の修正 | 一部不可 | 施設編集画面（全項目変更可） | REQ-10 |
| QR分割単位の変更 | 不可 | QRペイロードルールマスタ | REQ-15 |
| 合数参照ロジックの変更 | 一部可 | 参照ロジックマスタ（直近参照を追加） | REQ-21 |

### 1.2 Django Admin の廃止

現行は `/admin/` で15モデルが直接編集可能な状態にある（A-12）。新システムではこれに相当する画面を持たない。理由は次のとおり。

バリデーションを経ずにデータを更新できるため、業務ルールに反するデータが混入する。関連レコードへの影響（有効期間の整合性、帳票への遡及）が考慮されない。操作の記録が業務監査ログとして残らない。

代わりに、Django Admin で行っていた操作すべてに対応する専用マスタ画面を用意する（FR-201）。緊急時のデータ修正は、システム管理者権限の専用画面 + 承認フロー + 監査ログで対応する。

### 1.3 マスタの3分類

| 分類 | 特徴 | 例 | 変更の影響 |
|------|------|-----|-----------|
| **区分マスタ** | コード値の集合。並び順を持つ | 食事区分、献立種類、嚥下食区分、アレルギー種類 | 追加は即時反映。削除は論理削除 |
| **ルールマスタ** | 業務ロジックのパラメータ | 締切ルール、製造パターン、参照ロジック、資料出力ルール | 有効期間で管理。過去に遡及しない |
| **紐付けマスタ** | 施設・商品への設定割当 | 施設別アレルギー、施設別参照ロジック、単価 | 有効期間で管理 |

ルールマスタと紐付けマスタは必ず有効期間（`valid_from` / `valid_to`）を持つ。これが REQ-16「食種変更で過去資料が変わる」の構造的な予防策になる。

## 2. マスタ共通仕様（FR-201）

### 2.1 一覧画面の共通要素

| 要素 | 仕様 |
|------|------|
| 検索 | キーワード検索（対象カラムはマスタごとに定義）。日本語部分一致に対応 |
| 絞込 | 有効/無効、カテゴリ、有効期間（基準日指定） |
| 並び替え | 列ヘッダークリック。**並び順はユーザー単位で永続化**（REQ-18） |
| 表示順の変更 | ドラッグ&ドロップ。即時保存。`sort_order` を再割当 |
| 表示件数 | 20 / 50 / 100 / 200 |
| ページング | サーバーサイド（NFR-18-1） |
| 論理削除の表示 | 既定で非表示。「削除済みを含む」トグルで表示 |
| 一括操作 | 有効化/無効化、削除、CSVエクスポート |
| 状態の保持 | 絞込・並び順・ページ位置を URL クエリに反映（FR-005） |

### 2.2 編集画面の共通要素

| 要素 | 仕様 |
|------|------|
| バリデーション | クライアント（Zod）とサーバー（同一スキーマ）の両方で実施 |
| 影響範囲の表示 | 保存前に影響を受けるレコード件数を表示（例: 「この変更は将来の注文 1,204 件に影響します」） |
| 有効期間の指定 | ルールマスタ・紐付けマスタは「いつから適用するか」を必ず指定 |
| 未来日付の予約 | `valid_from` に未来日を指定して変更を予約できる |
| 変更履歴 | 画面内に監査ログの該当分を表示 |
| 削除時の確認 | 影響範囲を明示し、削除理由の入力を求める |

### 2.3 CSV インポート／エクスポート

361施設・約2,700商品規模のマスタを画面操作のみで維持するのは非現実的なため、全マスタで CSV 入出力を提供する。

| 項目 | 仕様 |
|------|------|
| エクスポート | 現在の絞込条件を反映。ヘッダー行にカラム名（日本語）を含む |
| インポート | ドライラン（検証のみ）を必須の第1ステップとする |
| 検証内容 | 必須項目、型、外部キーの存在、有効期間の重複、一意制約 |
| 結果表示 | 追加N件 / 更新N件 / エラーN件を行番号付きで表示 |
| 実行 | 検証を通過した内容のみを単一トランザクションで適用 |
| ロールバック | インポート単位で取消できる |

## 3. 締切ルール（REQ-13）

FR-205, FR-206。要望のうち運用負荷が最も高い項目。

### 3.1 締切の解決ロジック

```
入力: 注文種別, 施設ID, 対象喫食日
出力: 締切日時

1. 例外日を検索（order_deadline_exceptions）
   - 対象喫食日が target_service_date_from〜to に含まれるか
   - スコープの優先順位: customer > customer_group > global
   - recurrence='yearly' の場合は年を無視して月日で判定
   → 見つかれば deadline_at をそのまま返す（終了）

2. 通常ルールを検索（order_deadline_rules）
   - スコープの優先順位: customer > customer_group > global
   - 対象喫食日が valid_from〜valid_to に含まれるもの

3. 締切日時を算出
   - deadline_weekday が NULL の場合:
       締切日 = 対象喫食日 - lead_days
   - deadline_weekday が指定されている場合:
       締切日 = (対象喫食日 - lead_days) 以前の直近の該当曜日
   - 締切日時 = 締切日 + deadline_time

4. 営業日カレンダーで調整
   - 締切日が休業日の場合は直前の営業日に前倒し
```

### 3.2 締切ルールマスタ画面

| 項目 | 入力形式 | 必須 | 備考 |
|------|---------|------|------|
| 注文種別 | select | ○ | 仮注文 / 食数変更 / 合数指定 / アレルギー / 元旦注文 / 特別注文 |
| 適用範囲 | radio | ○ | 全体 / 施設グループ / 個別施設 |
| 対象 | 検索付きselect | 適用範囲に応じて | 施設グループまたは施設 |
| リードタイム | number（日） | ○ | 喫食日の何日前 |
| 締切曜日 | select | — | 未指定の場合はリードタイムのみで判定 |
| 締切時刻 | time | ○ | **既定値 17:00**（現行踏襲） |
| 変更可能期間 | number（日） | — | 締切後に変更を許可する日数 |
| 適用開始日 | date | ○ | — |
| 適用終了日 | date | — | 未指定は無期限 |

**保存時の検証**

- 同一注文種別・同一スコープで有効期間が重複していないこと
- 変更により締切が過去になる注文が発生しないこと（発生する場合は警告して確認を求める）
- 影響を受ける施設数と将来注文件数を保存前に表示する

### 3.3 締切例外日マスタ画面

正月の前倒しがこの画面で完結する。REQ-13 の直接的な回答。

| 項目 | 入力形式 | 必須 | 備考 |
|------|---------|------|------|
| 例外名 | text | ○ | 例: `2027年正月前倒し` |
| 注文種別 | multi-select | — | 未指定は全種別 |
| 適用範囲 | radio | ○ | 全体 / グループ / 個別 |
| 対象喫食日（開始） | date | ○ | 例: `2027-01-01` |
| 対象喫食日（終了） | date | ○ | 例: `2027-01-03` |
| 締切日時 | datetime | ○ | 例: `2026-12-20 10:00` |
| 繰り返し | radio | ○ | なし / 毎年 |
| 理由 | textarea | — | — |

**操作フロー**

```
1. 「例外日を追加」をクリック
2. 対象喫食日と締切日時を入力
3. 「影響を確認」→ 対象施設数・該当注文の入力状況を表示
4. 「保存」→ 即時反映
5. 対象施設へ自動通知（FR-003）
```

現行は社内担当者が開発者へ依頼していた作業が、この5ステップで完了する。

### 3.4 締切の表示仕様（FR-206）

| 表示箇所 | 内容 |
|---------|------|
| 全注文画面の上部 | `次回締切: 8月12日(火) 17:00まで（残り 2日 4時間）` |
| 締切1時間前以降 | 赤色の強調表示 + 残り時間を分単位で表示 |
| 締切超過分 | 入力欄を非活性化し、`締切を過ぎています（8月12日 17:00締切）` と表示 |
| 締切カレンダー | 喫食日ごとの締切日時を月間カレンダーで一覧 |
| 変更可能期間 | `8月14日 〜 8月19日 喫食分が変更可能です`（現行の表現を踏襲） |

現行は元旦注文のみ締切時刻を表示していた（「10時までに」）。この表示を全画面へ展開する。

### 4.3 区分追加時の自動反映（REQ-09）

区分を1件追加したときに、以下が**コード変更なしで**追随することを要件とする。

```
1. 嚥下食区分マスタに「あんかけ食」を追加（表示順4）
2. 食種マスタで嚥下食区分「あんかけ食」を選択した食種を作成
3. 献立種類マスタで当該食種の献立を作成
   ↓
4. 週間注文入力画面に列が自動追加される
5. 各帳票の集計単位に自動的に含まれる
6. 盛付指示書の定型文で対象区分として選択できる
```

**受入テストシナリオ**: 業務担当者が上記1〜3を実施し、4〜6が開発者の介入なく成立することを確認する（NFR-16-5）。

## 5. 製造パターン・集荷日・着日（REQ-08）

FR-204, FR-505。

### 5.1 D0〜D3 の定義

`[要確認]` 現行システムで該当設定を発見できなかったため、以下の解釈で設計する。合意時に確定させる。

| 表記 | 解釈 |
|------|------|
| D0 | 製造日当日 |
| D1 | 製造日の翌日 |
| D2 | 製造日の2日後 |
| D3 | 製造日の3日後 |

集荷日は D0〜D3、着日は D1〜D3 の範囲を取る。着日は集荷日以降でなければならない。

### 5.2 製造パターンマスタ画面

| 項目 | 入力形式 | 必須 | 備考 |
|------|---------|------|------|
| コード | text | ○ | — |
| パターン名 | text | ○ | 例: `D0集荷-D1着（近距離）` |
| 集荷オフセット | select（D0〜D3） | ○ | — |
| 着荷オフセット | select（D1〜D3） | ○ | 集荷オフセット以上 |
| 配送業者 | select | — | 佐川急便 / 自社便 / その他 |
| 適用地域 | multi-select | — | 都道府県 |
| 有効 | toggle | ○ | — |

**画面上の可視化**: 選択したオフセットに基づき、製造日を起点としたタイムラインを図示する。

```
製造日(D0)  D1        D2        D3
  │         │         │         │
  ▼集荷     ▼着荷
  8/18      8/19  ← 喫食日 8/20 の場合
```

### 5.3 施設への割当

| 項目 | 入力形式 | 必須 |
|------|---------|------|
| 対象 | 施設 or ユニット | ○ |
| 製造パターン | select | ○ |
| 適用開始日 | date | ○ |
| 適用終了日 | date | — |

**保存時の検証**

- 同一対象の有効期間が重複しないこと
- 変更により既に確定した配送予定と矛盾が生じないこと（生じる場合は影響一覧を表示）

### 5.4 日付算出の営業日調整

営業日カレンダー（`business_calendar`）を参照し、以下を考慮する。

| 条件 | 調整 |
|------|------|
| 集荷日が非配送日 | 前営業日へ前倒し |
| 着日が非配送日 | 翌営業日へ後倒し。ただし喫食日を超える場合はエラーとして警告 |
| 製造日が非製造日 | 前製造日へ前倒し |

## 6. 献立定型文（REQ-18）

FR-207, FR-403。要望原文で4つの課題が明示されている項目。

### 6.1 課題と対応の対照

| 要望原文の課題 | 対応する仕様 |
|--------------|-------------|
| クリックしないと内容が分からない | 一覧に本文プレビュー列（先頭100文字）を表示。ホバーで全文をポップオーバー表示 |
| 並び替えても作業をすると元に戻る | 並び順をユーザー単位で永続化（`user_list_preferences`） |
| 検索がしにくい | 本文の全文検索（MySQL ngram パーサー）+ カテゴリ・タグ・対象区分での絞込 |
| 整理がしにくい / どんどん増えて整理できていない | 重複候補の検出、使用回数・最終使用日の表示、未使用の一括アーカイブ |

### 6.2 一覧画面

| 列 | 内容 |
|----|------|
| 短縮名 | 現行踏襲 |
| 本文プレビュー | 先頭100文字。全文はホバー表示 |
| 対象区分 | 基本食用 / 嚥下用（嚥下用は区分名も表示） |
| カテゴリ | — |
| タグ | 複数表示 |
| 使用回数 | 降順ソート可 |
| 最終使用日 | 未使用は `—` を表示 |
| 状態 | 有効 / アーカイブ済 |

**絞込条件**

キーワード（本文・短縮名の全文検索）、対象区分、嚥下食区分、カテゴリ、タグ、使用回数（0件のみ / 1回以上）、最終使用日（N日以上未使用）、状態

### 6.3 重複検出

| 項目 | 仕様 |
|------|------|
| 検出方法 | 本文を正規化（空白・改行・記号の統一）した SHA-256 ハッシュの一致で完全重複を検出 |
| 類似検出 | `[設計案]` 正規化後の文字列の類似度（レーベンシュタイン距離ベース）が閾値以上のものを候補表示 |
| 統合操作 | 重複候補を選択して「統合」。統合先を指定し、統合元を参照している既存の盛付指示書には影響しない（`body_snapshot` を保持しているため） |

### 6.4 アーカイブ

| 項目 | 仕様 |
|------|------|
| 条件指定 | 「N日以上未使用」「使用回数0件」で対象を抽出 |
| 一括アーカイブ | 抽出結果を確認して一括実行 |
| 影響 | 新規の盛付指示書作成時の選択肢から除外される。**過去の盛付指示書の内容は変わらない** |
| 復元 | アーカイブ済みを検索して個別に復元できる |

過去の指示書が影響を受けないのは、`setout_instruction_lines.body_snapshot` に本文のコピーを保持しているため（`05_data_model.md` §6.5）。

## 7. 施設別アレルギー設定（REQ-12）

FR-208。

### 7.1 画面仕様

| 項目 | 入力形式 | 必須 |
|------|---------|------|
| 施設 | 検索付きselect | ○ |
| アレルギー種類 | multi-select（頻発を上部に表示） | ○ |
| 適用開始日 | date | ○ |
| 適用終了日 | date | — |

一覧では施設ごとに設定済みアレルギーをタグ表示し、個別に削除できる。

### 7.2 削除仕様

要望原文が「間違えて登録したりもするので」であることから、誤登録の取り消しが主用途である。

| 項目 | 仕様 |
|------|------|
| 削除方式 | 論理削除（`deleted_at`） |
| 削除理由 | 選択式（誤登録 / 契約変更 / その他）+ 自由記述 |
| 影響範囲の表示 | 削除前に「このアレルギー設定を参照している未確定の注文 N 件」を表示 |
| 未確定注文への対応 | 削除と同時に該当注文を取り消すか、注文は残すかを選択できる |
| 過去データ | 確定済みの注文・生成済みの帳票には影響しない |
| 復元 | 削除済み一覧から復元できる |

## 8. 資料出力ルール（REQ-11, REQ-16, REQ-17）

FR-209, FR-401, FR-402。

### 8.1 ルールの構造

食種と資料種別の組み合わせで出力可否を定義する。

| 食種 | 献立表 | 栄養月報 | アレルギー表 | 汁物資料 |
|------|-------|---------|------------|---------|
| 常食 | ✅ | ✅ | ✅ | ✅ |
| 薄味 | ✅ | ✅ | ✅ | ✅ |
| 汁無し | ✅ | ✅ | ✅ | ❌ |

### 8.2 画面仕様

| 項目 | 入力形式 |
|------|---------|
| 食種 × 資料種別のマトリクス | チェックボックスのグリッド |

| 適用終了日 | date |

施設固有の上書きは施設編集画面の「資料出力」タブで設定する。

### 8.3 食種変更時の挙動（REQ-16 の解決）

```
施設Aの食種を「常食」から「汁無し」へ 2026-09-01 から変更する

1. 施設編集画面で食種を変更、適用開始日に 2026-09-01 を指定
2. システムが影響範囲を表示
   - 2026-09-01 以降の喫食日を対象とする資料: 生成時に汁物資料を除外
   - 2026-08-31 以前の喫食日を対象とする資料: 影響なし（生成済みのものは変更されない）
3. 保存
   - customer_settings に新しい有効期間の行を追加
   - 既存行の valid_to を 2026-08-31 に更新
4. 結果
   - 過去の資料を開いても内容が変わらない（settings_snapshot を参照）
   - 9月以降の資料生成時に自動的に汁物資料が除外される
```

**受入テストシナリオ**: 8月分の資料を生成 → 食種を9月から変更 → 8月分の資料を再度開いて内容が変わっていないことを確認する（NFR-08-6）。これが REQ-16 の検証条件である。

## 9. 参照ロジック（REQ-21）

FR-704。現行361施設に設定されている。

### 9.1 参照パターンの一覧

| コード | 名称 | 戦略 | 説明 |
|-------|------|------|------|
| `basic` | 基本パターン | `same_menu_past` | 過去の同一献立の合数を参照（現行の既定） |
| `latest` | **直近の実績を参照** | `latest_actual` | **REQ-21 で新規追加**。直近の合数実績を参照 |
| `contract_expired_zero` | 契約切れ注文0 | `none` | 0として扱う |
| `lunch_only` | 昼のみ注文 | `same_menu_past` | 昼食のみを対象 |
| `breakfast_only` | 朝のみ注文 | `same_menu_past` | 朝食のみを対象 |
| `mon_tue_thu_sat` | 月火木土のみ注文 | `same_menu_past` | 曜日条件付き |

現行の確認済みパターンに `latest` を追加する構成。

### 9.2 フォールバック設定

REQ-21 の要望「1年に1回しか入ってないようなものは直近の合数を取りに行く方がいい」を、フォールバックの組み合わせで表現する。

| 項目 | 入力形式 | 説明 |
|------|---------|------|
| 参照戦略 | select | 過去同一献立 / 直近実績 / 固定値 / 参照しない |
| 参照上限日数 | number | 過去同一献立の場合、参照元データが何日以内であることを要求するか |
| フォールバック先 | select（参照ルール） | 上限を超えた場合に使用するルール |
| 固定値 | number | 固定値戦略の場合 |

**設定例（REQ-21 の要望を満たす設定）**

```
参照戦略: 過去同一献立
参照上限日数: 180
フォールバック先: 直近の実績を参照
```

この設定により、過去同一献立のデータが180日以内にあればそれを使い、なければ直近実績を使う。年1回しか登場しない献立では自動的に直近実績が採用される。

### 9.3 施設への割当画面

| 項目 | 仕様 |
|------|------|
| 一覧 | 361施設の一覧。施設名・現在の参照ルール・最終適用日を表示 |
| 絞込 | 施設名検索、参照ルール、未設定のみ |
| 個別設定 | 施設 × 献立種類単位で設定。献立種類を指定しない場合は施設全体 |
| 一括設定 | 選択した複数施設に同一ルールを適用 |
| CSVインポート | 361件を一括更新 |
| プレビュー | 指定喫食日について「どの施設がどのデータを参照するか」を試算表示 |

プレビュー機能により、設定変更の結果を発注量計算の実行前に確認できる。

### 9.4 適用結果の追跡

`mix_rice_logs` に適用結果を記録し、合数ログ（FR-709）で検証できる。

| 記録項目 | 内容 |
|---------|------|
| 適用ルール | どのルールが適用されたか |
| 参照元喫食日 | どの日のデータを参照したか |
| フォールバック発生 | 上限超過によりフォールバックしたか |
| 採用値 | 最終的に使用した合数 |

新規施設の登録時は、必須項目のみのウィザード形式とし、詳細設定は登録後に編集する。

```
Step 1: 基本情報（施設コード・名称・住所・契約開始日）

Step 3: 食種・献立種類
Step 4: 単価
Step 5: 確認・登録
  ↓
登録完了後、詳細設定（配送・資料・アレルギー・発注）は編集画面で設定
```

登録後にすべての項目を変更できることを要件とする（REQ-10）。
