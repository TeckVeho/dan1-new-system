# 00. 背景・目的・スコープ

作成日: 2026-08-04

---

## 1. 背景

株式會社 談 は、介護施設・医療施設向けに食事（常食・薄味食・嚥下食等）を製造・配送している。現在の業務は2つのシステムで運営されている。

| システム | URL | 役割 | 利用者 |
|---------|-----|------|--------|
| 基幹システム | `https://order.dan1.jp/` | 施設からの受注、献立資料配布、製造帳票・請求書生成 | 施設ユーザー（361施設）＋ 社内管理者 |
| 発注・在庫確認システム | `http://35.75.152.221/` | 仕入業者への発注量計算、棚卸、在庫管理 | 社内6名（栄養士2名＋事務1名が主利用） |

両システムは同一認証で連携しているが、独立したアプリケーションとして稼働しており、次の構造的な問題を抱えている。

**運用が開発者依存になっている。** 締切変更、嚥下食の欄追加、施設食種の変更に伴う資料出力設定などがマスタ画面から行えず、都度開発者への依頼が必要になっている。クライアントの改善要望24項目のうち6項目が「マスタでできない」に起因する。

**設定変更が過去データに遡及する。** 施設の食種を変更すると、過去に生成済みの献立資料まで内容が書き換わる。帳票が生成時点の設定のスナップショットを保持していないためと推定される。

**排他制御が粗く、同時作業ができない。** 発注・在庫システムは仕入業者単位でロックを取得する方式で、1ユーザーが1業者を占有する。一般社員は他人のロックを解除できず、管理者の介入が必要になる。

**重い処理が同期実行されている。** 発注スケジュールは商品×納品日のマトリクスで、1セルに7行以上の数値を持つ情報密度の高い画面である。寿屋商事・ショクカイの1週間分を出力すると極端に遅くなる。食数取込も「1週間程度を目安」と画面上で制限されている。

**主要画面が停止している。** メインの注文入力画面 `/order/` は施設ユーザー（99999）・管理者（91001）双方で HTTP 500 を返しており、調査時点で使用不可だった。

**インフラが統一されていない。** 基幹は独自ドメイン（`order.dan1.jp`）だが、発注・在庫システムは IP アドレス直打ち（`35.75.152.221`）で HTTP 平文通信。2システム間で予測困難なリダイレクトが発生する。

## 2. 目的

| # | 目的 | 達成指標 |
|---|------|---------|
| 1 | 運用の自律化 | 開発者依頼が必要な設定変更をゼロにする（現行6領域） |
| 2 | データ整合性の確保 | 設定変更が過去帳票に遡及しない。帳票は生成時点の内容を再現可能 |
| 3 | 同時作業性の向上 | 社内ユーザーが業者を問わず同時に発注作業できる |
| 4 | 応答性能の改善 | 発注スケジュール1週間分の表示を目標値内に収める（NFR-01） |
| 5 | 業務のシステム内完結 | FAX・手作業に残る業務（佐川伝票、おせち容器注文、試食会）をシステムに取り込む |
| 6 | 基盤の統一 | 単一ドメイン・単一認証・HTTPS 化 |

## 3. スコープ

### 3.1 対象範囲

基幹システムと発注・在庫確認システムの**全機能を単一の新システムに統合**する。

| 領域 | 現行の所在 | 新システムでの扱い |
|------|-----------|------------------|
| 施設向け受注 | 基幹（施設ユーザー画面 12画面） | 統合。UI全面刷新 |
| マスタメンテナンス | 基幹 `/master/index`（約25画面） | 統合。設定駆動へ再設計 |
| 社内業務（帳票・配送・請求） | 基幹 `/control-panel`（50機能超） | 統合。カテゴリ再編 |
| データベース直接編集 | 基幹 `/admin/`（Django Admin 15モデル） | **廃止**。マスタ画面に機能吸収 |
| 発注量計算・スケジュール | 在庫システム `/schedule` | 統合。非同期化＋絞込機能追加 |
| 棚卸・在庫 | 在庫システム | 統合 |
| 仕入業者・商品マスタ | 在庫システム | 統合。基幹マスタと統一 |

### 3.2 対象外（スコープ外）

| 項目 | 理由 |
|------|------|
| らくらく献立（献立作成ソフト）本体 | 外部パッケージ。Excel 連携のみ継続 |
| HACCP アプリ | 別システム。社員番号の対応管理のみ行う |
| コーポレートサイト（`www.dan1.jp`） | 業務システムと無関係 |
| 会計システム | `[要確認]` 請求データの連携先が未特定 |

### 3.3 スコープ境界の判断が必要な項目

| 項目 | 状況 | 判断 |
|------|------|------|
| QRコード生成 | 現行 Web UI 上に一切存在せず、別プロセスまたはオフライン生成と推定 | 新システム内で生成する前提で設計。`[要確認]` |
| 佐川急便連携 | CP に「佐川伝票用ファイル一覧」があり、ファイル出力までは実装済み | 送り状 API 連携まで自動化。`[要確認]` API 契約の有無 |
| 売価計算 | CP に売価計算表出力・管理あり | 統合対象に含む |

## 4. 技術スタック

### 4.1 決定事項

| レイヤ | 採用技術 | 補足 |
|--------|---------|------|
| フロントエンド | Next.js 15（App Router）/ TypeScript / React 19 | 施設向け・社内向けを単一アプリのルートグループで分離 |
| スタイリング | Tailwind CSS | データ密度の高い表組みに対応するトークン設計を別途定義 |
| バックエンド | Express 5 / TypeScript | REST API。`apps/api` |
| ORM | Prisma | MySQL 向け。新規スキーマなので `prisma migrate` で管理 |
| データベース | MySQL 8.0（Cloud SQL） | 新規構築。文字セット `utf8mb4`、照合順序 `utf8mb4_0900_ai_ci` |
| 非同期処理 | Cloud Tasks + Cloud Run Jobs | 帳票生成・データ取込 |
| ファイルストレージ | Cloud Storage | 帳票・献立資料・アップロードファイル |
| 認証 | 自前実装（セッション or JWT）+ Secret Manager | 詳細は `10_auth_roles.md` |
| インフラ | Google Cloud Platform | 詳細は `11_infrastructure.md` |

### 4.2 モノレポ構成

```
dan1-new-system/
├── apps/
│   ├── web/              # Next.js（施設向け + 社内向け）
│   └── api/              # Express REST API
├── packages/
│   ├── database/         # Prisma スキーマ・マイグレーション・生成クライアント
│   ├── shared/           # 型定義・バリデーションスキーマ（Zod）・定数
│   └── ui/               # 共通UIコンポーネント（misaki-reports 準拠。詳細は 15_ui_design_spec.md）
├── jobs/                 # Cloud Run Jobs（帳票生成・取込・定期実行）
├── infra/                # Terraform
├── docs/                 # 本要件定義
└── package.json          # npm workspaces
```

**UIデザイン。** 見た目・シェルレイアウトは既存プロダクト `misaki-reports`（`/Users/kohei/Projects/misaki-reports`）と同一系統とする。トークン・コンポーネント仕様は `15_ui_design_spec.md`。

### 4.3 技術選定の根拠

**MySQL を新規構築とする判断の影響。** 既存 DB スキーマを踏襲しないため、データモデルは業務要件から再設計する（`05_data_model.md`）。これにより現行の設計上の制約（設定の遡及適用など）を持ち込まずに済む一方、既存データの移行にはマッピング作業が発生する（`12_migration_plan.md`）。

**Prisma を選ぶ理由。** 新規スキーマのためマイグレーション管理が主用途になり、`prisma migrate` の宣言的スキーマ管理が適合する。発注スケジュールのような複雑な集計クエリは Prisma の raw query（`$queryRaw`）で書き、型は手動定義する方針とする。

**Cloud Run を選ぶ理由。** 社内利用者は10名程度、施設ユーザーも締切前（平日17:00付近）にピークが集中する。常時稼働のワークロードではないため、リクエスト課金でスケールする Cloud Run が費用効率に合う。ただし締切直前のコールドスタートを避けるため最小インスタンス数を確保する（`11_infrastructure.md`）。
