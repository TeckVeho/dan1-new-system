# 04. 非機能要件

作成日: 2026-08-04

現行システムの性能課題（REQ-22, REQ-23）が定性的な訴えのみで数値化されていないため、目標値は業務影響から逆算した仮置き値とし `[要確認]` を付す。合意時に確定させる。

## 2. 可用性・信頼性

### NFR-06 可用性

| ID | 項目 | 要件 |
|----|------|------|
| NFR-06-1 | サービス稼働率 | 99.5%（月間ダウンタイム約3.6時間以内） |
| NFR-06-2 | 計画停止 | 月1回・深夜2〜5時・事前告知3営業日前 |
| NFR-06-3 | 業務クリティカル時間帯 | 平日 8:00〜19:00 は計画停止を行わない。特に締切時刻（既定17:00）前後2時間 |
| NFR-06-4 | 月末月初 | 請求処理期間（月末3営業日〜翌月5営業日）は計画停止を行わない |

99.9% ではなく 99.5% とする理由は、社内10名規模・施設の注文が締切までに完了すれば足りる業務特性のため。ただし締切直前の停止は業務に直結するため NFR-06-3 で時間帯を制約する。

### NFR-07 障害復旧

| ID | 項目 | 要件 | 実現手段 |
|----|------|------|---------|
| NFR-07-1 | RPO（目標復旧時点） | 1時間 | Cloud SQL 自動バックアップ + PITR（バイナリログ） |
| NFR-07-2 | RTO（目標復旧時間） | 4時間 | Cloud Run の再デプロイ + Cloud SQL リストア |
| NFR-07-3 | バックアップ | 日次フルバックアップ（保持30日）+ PITR（7日） | Cloud SQL 自動バックアップ |
| NFR-07-4 | ファイルの冗長化 | リージョン内冗長 + 別リージョンへの日次複製 | Cloud Storage デュアルリージョン `[要確認]` コスト |
| NFR-07-5 | リストア訓練 | 年2回 | 手順書を `12_migration_plan.md` に付随して整備 |

### NFR-08 データ整合性

| ID | 項目 | 要件 |
|----|------|------|
| NFR-08-1 | トランザクション | 注文保存・請求締め・発注確定は単一トランザクションで整合性を保つ |
| NFR-08-2 | 楽観ロック | 同時更新の競合を検出し、silent overwrite を発生させない（FR-307） |
| NFR-08-3 | ジョブの冪等性 | 同一ジョブの再実行で結果が変わらない。取込は重複検出する |
| NFR-08-4 | 外部キー制約 | 参照整合性を DB 制約で保証する。論理削除は制約と両立させる |
| NFR-08-5 | 設定の有効期間 | 同一対象の有効期間が重複しないことを DB 制約またはアプリ検証で保証する（FR-202） |
| NFR-08-6 | 帳票の不変性 | 生成済み帳票のスナップショットは更新・削除できない（FR-402） |

## 3. セキュリティ

### NFR-09 通信・暗号化

| ID | 項目 | 要件 |
|----|------|------|
| NFR-09-1 | 通信の暗号化 | 全通信を HTTPS（TLS 1.2以上）とする。HTTP は HTTPS へリダイレクト |
| NFR-09-2 | HSTS | `Strict-Transport-Security` を設定する |
| NFR-09-3 | 保存データの暗号化 | Cloud SQL・Cloud Storage の保存時暗号化（GCP 既定の CMEK 相当） |
| NFR-09-4 | 機密情報の管理 | DB 接続情報・API キーは Secret Manager に格納し、コード・環境変数に平文で置かない |

現行の発注・在庫システムは HTTP 平文（`http://35.75.152.221/`）で認証情報を送信している。これは NFR-09-1 で解消される（REQ-01）。

### NFR-10 認証・認可

| ID | 項目 | 要件 |
|----|------|------|
| NFR-10-1 | パスワード保存 | Argon2id でハッシュ化する |
| NFR-10-2 | パスワードポリシー | 12文字以上、英大小文字・数字・記号のうち3種以上、ログインIDと同一を禁止 `[要確認]` |
| NFR-10-3 | 多要素認証 | 社内管理者は必須、社内一般は推奨（FR-102） |
| NFR-10-4 | アカウントロック | ログイン失敗5回で15分ロック |
| NFR-10-5 | セッション | HttpOnly / Secure / SameSite=Lax の Cookie。社内8時間・施設24時間で失効 `[要確認]` |
| NFR-10-6 | 権限検証 | すべての API でサーバー側の権限検証を行う。画面側の制御のみに依存しない |
| NFR-10-7 | 施設データの分離 | 施設ユーザーは自施設のデータのみアクセス可。API のクエリレベルで強制する |
| NFR-10-8 | 特権操作の記録 | 成り代わり・強制解除・マスタ変更・請求訂正はすべて監査ログに記録する |

現行の「パスワード = ログインID」（A-01）と Django Admin の無制限データ編集（A-12）は NFR-10-1, NFR-10-2, NFR-10-6 で解消される。

### NFR-11 脆弱性対策

| ID | 項目 | 要件 |
|----|------|------|
| NFR-11-1 | SQLインジェクション | ORM のパラメータバインドを使用する。raw query も必ずバインドする |
| NFR-11-2 | XSS | React の自動エスケープに依存し、`dangerouslySetInnerHTML` を原則禁止する |
| NFR-11-3 | CSRF | SameSite Cookie + CSRF トークン |
| NFR-11-4 | 入力検証 | API の入力を Zod スキーマで検証する。型定義とスキーマを共有パッケージで一元化する |
| NFR-11-5 | ファイルアップロード | 拡張子・MIME タイプ・サイズ（既定20MB）を検証する。実行可能ファイルを拒否する |
| NFR-11-6 | ファイルダウンロード | 有効期限付き署名付きURL（既定15分）。URL 推測によるアクセスを防ぐ |
| NFR-11-7 | 依存パッケージ | Dependabot による脆弱性検知と月次更新 |
| NFR-11-8 | セキュリティヘッダー | CSP・X-Content-Type-Options・X-Frame-Options を設定する |
| NFR-11-9 | レート制限 | ログイン試行・API 呼び出しにレート制限を適用する |
| NFR-11-10 | アクセス制限 | 社内向け画面へのアクセスを IP 制限できる（任意設定） `[要確認]` 拠点の固定IPの有無 |

### NFR-12 個人情報保護

| ID | 項目 | 要件 |
|----|------|------|
| NFR-12-1 | 対象データ | 施設の担当者名・連絡先、社員の氏名・社員番号・HACCP番号 |
| NFR-12-2 | ログへの出力禁止 | 個人情報・認証情報をアプリケーションログに出力しない |
| NFR-12-3 | 開発環境のデータ | 本番データを開発環境で使用する場合はマスキングする |
| NFR-12-4 | アクセス権の最小化 | 開発者の本番DB直接アクセスを原則禁止し、必要時は承認と記録を伴う |

## 4. 運用・保守

### NFR-13 監視・ログ

| ID | 項目 | 要件 |
|----|------|------|
| NFR-13-1 | アプリケーションログ | Cloud Logging に構造化ログ（JSON）で出力。リクエストIDで追跡可能 |
| NFR-13-2 | エラー通知 | Error Reporting でエラーを集約し、重大度に応じて通知する |
| NFR-13-3 | メトリクス監視 | レスポンスタイム・エラー率・DB接続数・ジョブ滞留数を監視する |
| NFR-13-4 | アラート条件 | エラー率5%超（5分継続）、P95応答時間が目標の2倍超、ジョブ失敗、DB CPU 80%超 |
| NFR-13-5 | 死活監視 | ヘルスチェックエンドポイントを1分間隔で監視する |
| NFR-13-6 | 分散トレース | Cloud Trace で API → DB → ジョブの処理時間を可視化する |
| NFR-13-7 | 監査ログの分離 | 業務監査ログ（FR-001）はDBに保持し、システムログとは別管理とする |

現行はバージョン表記の不一致（A-04）やパッケージ単位画面の初回500エラー（A-08）といった事象が放置されている。NFR-13-2, NFR-13-4 により検知できる状態にする。

### NFR-14 デプロイ・リリース

| ID | 項目 | 要件 |
|----|------|------|
| NFR-14-1 | CI/CD | GitHub Actions からのビルド・テスト・デプロイの自動化 |
| NFR-14-2 | 環境 | 開発 / ステージング / 本番の3環境 |
| NFR-14-3 | デプロイ方式 | Cloud Run のリビジョン切替による無停止デプロイ。段階的トラフィック移行 |
| NFR-14-4 | ロールバック | 直前のリビジョンへ5分以内に戻せる |
| NFR-14-5 | DBマイグレーション | 後方互換を保った段階適用（列追加 → コード反映 → 旧列削除） |
| NFR-14-6 | バージョン表示 | 全画面に単一のバージョン番号を表示する（A-04 の解消） |

### NFR-15 テスト

| ID | 項目 | 要件 |
|----|------|------|
| NFR-15-1 | ユニットテスト | 業務ロジック（発注量計算・締切判定・有効期間解決・参照ロジック）のカバレッジ80%以上 |
| NFR-15-2 | 統合テスト | API の主要エンドポイントに対するテスト |
| NFR-15-3 | E2Eテスト | 主要業務フロー（注文入力 → 締切 → 取込 → 発注 → 帳票）を Playwright で自動化 |
| NFR-15-4 | 性能テスト | NFR-01, NFR-03 の目標値をリリース前に検証する。本番同等のデータ量で実施 |
| NFR-15-5 | 移行テスト | 本番データのコピーで移行リハーサルを2回以上実施する（`12_migration_plan.md`） |

性能テストは NFR-01-4（発注スケジュール）を最重要項目とする。REQ-22, REQ-23 が本プロジェクトの主要な改善目標であり、目標未達のままリリースすると要望が満たされない。

### NFR-16 保守性

| ID | 項目 | 要件 |
|----|------|------|
| NFR-16-1 | 型安全性 | TypeScript の strict モード。API の入出力型をフロント・バックで共有する |
| NFR-16-2 | コード規約 | ESLint + Prettier による自動チェック。CI で強制する |
| NFR-16-3 | 設定の外部化 | 業務ルール（締切・製造パターン・参照ロジック等）をコードに埋め込まない（FR-2xx の前提） |
| NFR-16-4 | ドキュメント | API 仕様を OpenAPI で管理し、コードから自動生成する |
| NFR-16-5 | 開発者依頼の削減 | マスタ変更・設定変更で開発者の介入が必要な操作をゼロにする（REQ-02） |

NFR-16-3 と NFR-16-5 は本プロジェクトの中心的な非機能要件である。現行システムの最大の課題は「マスタでできないことが多い」という運用上の制約であり、これは設定をコードに埋め込んだ設計に起因する。

|----|------|------|
| NFR-20-1 | らくらく献立への依存 | 献立データは外部パッケージの Excel 出力に依存する。ファイル形式変更のリスクを許容する |
| NFR-20-2 | 佐川急便 API | API 連携の可否が未確定。CSV 出力へのフォールバックを必須とする |
| NFR-20-3 | ラベルプリンタ | 対応フォーマットが未確定。出力形式を差し替え可能な設計とする |
| NFR-20-4 | HACCP アプリ | 番号の対応管理のみ。システム連携は行わない |
| NFR-20-5 | 既存DBスキーマ | 新規構築のため踏襲しない。データ移行時にマッピングが必要 |

### NFR-21 コスト制約

| ID | 項目 | 想定 |
|----|------|------|
| NFR-21-1 | GCP 月額費用 | `[要確認]` 予算上限。Cloud Run + Cloud SQL（db-custom-2-8192 想定）+ Storage で月額5〜10万円規模の見積 |
