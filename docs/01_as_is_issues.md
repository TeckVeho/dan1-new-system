## 凡例

| 記号 | 意味 |
|------|------|
| ✅ 確認済 | 実画面クロールで現行の状態を確認した |
| ⚠️ 一部確認 | 画面の存在は確認したが、詳細動作は未確認 |
| ❓ 未確認 | Web UI 上に該当機能を発見できなかった |
| 🐛 不具合 | 現行システムの明確な不具合 |

課題の分類:

| 分類 | 意味 |
|------|------|
| 設定不可 | マスタ画面から設定できず開発者依頼が必要 |

## 6. 発注・在庫システム

### REQ-21 合数未登録施設は直近の合数を参照する

| 項目 | 内容 |
|------|------|
| 分類 | データ整合性, 設定不可 |
| 要望原文 | 在庫システムで合数が入っていない施設：過去の同じ献立で取りに行くみたいだが、1年に1回しか入ってないようなものもあるのでこのような場合は直近の合数を取りに行く方がいい |
| 現行の状態 | ⚠️ `/reference-rule-settings`（参照ロジック設定）で361施設に対しパターンを設定できる。確認できたパターン例: 基本パターン、契約切れ注文0、昼のみ注文、朝のみ注文、月火木土のみ注文。**「直近参照」パターンの有無は未確認** |

| 業務影響 | 年1回程度しか登場しない献立では、過去同一献立の合数が古すぎて実態と乖離する。結果を `/orders/adjust`（食数補正）で手動補正している |
| 要件の本質 | 参照ロジックに「直近の合数を参照」を**選択可能なパターンとして追加**し、施設単位・献立単位で切り替える。フォールバック順序（過去同一献立 → 直近 → 既定値）も設定可能にする |

### REQ-22 複数人同時利用時のロード時間短縮

| 項目 | 内容 |
|------|------|
| 分類 | 性能 |
| 要望原文 | 在庫システム、複数人で使用しているとき特にロード時間が長い |
| 現行の状態 | ⚠️ **業者単位のロック機構**（`/lock-supplier`）が必須。1ユーザーが1業者を占有する。一般社員はロック解除不可で、管理者のみ `/user/unlock-supplier/` で強制解除できる。通知570件、参照ロジック361施設（13ページ）、商品119件でページング必須 |
| 根拠 | `02_screen_inventory_inventory.md` §6, `06_haccp_login_survey.md` §2.3 |
| 業務影響 | 3名の主利用者が同時に別業者を扱えるが、同一業者は排他。ロックが残ったまま離席すると他者が作業できない |
| 原因の推定 | ① 排他制御が業者単位という粗い粒度 ② 大量データを同期的に取得して画面描画（サーバーサイドページング未実施の可能性） ③ 発注量計算をリクエスト時に都度実行 |
| 要件の本質 | ① 排他制御をレコード単位の楽観ロックへ変更 ② サーバーサイドページング・仮想スクロール ③ 発注量計算の事前計算とキャッシュ |

### REQ-23 特定材料だけスケジュール出力

| 項目 | 内容 |
|------|------|
| 分類 | 性能, 未実装 |
| 要望原文 | 在庫システムで特定の現在に在庫を調べたいときに、寿屋・ショクカイを1週間分だそうとするとものすごく時間がかかるので、特定の材料だけスケジュールを出せたら良い |
| 現行の状態 | ⚠️ `/schedule` は業者×納品日範囲でグリッド表示。商品単位の絞込機能は未確認。納品日範囲を指定しないとグリッド自体が表示されない |
| 根拠 | `07_schedule_grid_survey.md` §2, §5 |
| 業務影響 | 1商品の在庫を確認するために業者の全商品×1週間分を出力する必要がある |
| 性能の構造的要因 | グリッドは1商品×1納品日のセルに**7行以上の数値**（計算前必要量・計算前注文数・必要量・注文数・喫食参照ラベル・発注数・仮在庫・見込み在庫・実在庫・注意）を持つ。商品119件×7日 = 833セル × 7行 ≈ 5,800要素を単一 HTML で描画している |
| 要件の本質 | ① 商品名・カテゴリでの絞込 ② 絞込条件を保存できるビュー機能 ③ 大量出力は非同期ジョブ化（Excel ダウンロード） |
