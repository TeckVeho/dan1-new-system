# 12. 移行計画

作成日: 2026-08-04

---

## 1. 移行の前提と制約

### 1.1 前提条件

| 項目 | 内容 |
|------|------|
| DB | **新規構築**。既存スキーマは踏襲しない（`05_data_model.md`） |
| 移行対象 | 既存データを新スキーマへマッピングして投入する |
| 既存システム | 移行完了後に停止する |
| 業務停止 | 最小化する。可能なら無停止に近い形とする |

### 1.2 最大のリスク

**既存 DB のスキーマとデータ内容が未確認である。** 本調査は Web UI のクロールのみで実施したため、以下が不明である。

| 不明点 | 影響 |
|--------|------|
| テーブル構成・カラム定義 | マッピング表が作成できない |
| データ量の実数 | 移行所要時間の見積ができない |
| データ品質（欠損・重複・不整合） | 移行時のクレンジング量が読めない |
| 食種マスタの所在と値 | REQ-11, REQ-16 の設計精度に直結 |
| 参照ロジックの設定内容（361施設分） | REQ-21 の初期データ |

**移行計画を確定させるには、既存 DB のスキーマ定義とサンプルデータの提供が必須である。** 本ドキュメントは提供を受ける前提での方針とタスクの整理であり、詳細なマッピング表は提供後に作成する。

### 1.3 移行方式の選択肢

| 方式 | 内容 | 業務停止 | リスク |
|------|------|---------|-------|
| **A. 一括切替（推奨）** | 全データを移行して一斉に新システムへ切替 | 1〜2日（週末） | 切り戻し判断が短時間 |
| B. 段階移行 | 機能ごとに順次移行し、期間中は2システム併用 | ほぼなし | 2システム間のデータ同期が複雑 |
| C. 並行運用 | 一定期間、両システムに同じデータを入力 | なし | 現場の二重入力負荷が大きい |

**方式A（一括切替）を推奨する。** 理由は次のとおり。

新システムは基幹と発注・在庫を統合するため、機能単位の段階移行では両システム間のデータ同期が必要になり、それ自体が現行の課題（2システム分離）を再現する。利用者が社内20名・施設361件と限られており、事前研修と並行テストで習熟を確保できる。月次の請求サイクルがあるため、月初の切替により請求データの分断を避けられる。

## 3. 移行の設計上の論点

### 3.1 有効期間の補完（最重要）

新システムは設定に有効期間を持たせる（FR-202）が、現行はおそらく単一の現在値のみを保持している。移行時に有効期間をどう設定するかが最も重要な判断になる。

| 選択肢 | 内容 | 影響 |
|--------|------|------|
| **A. 全て過去の十分早い日付から（推奨）** | `valid_from = '2000-01-01'`, `valid_to = NULL` | 過去の帳票を新システムで再生成すると現在の設定が適用される |
| B. 移行日から | `valid_from = 移行日`, `valid_to = NULL` | 移行日前の期間の設定が解決できず、過去データの参照でエラーになる |
| C. 契約開始日から | `valid_from = customers.contract_start_date` | 契約開始日が不明な施設で問題が生じる |

**方式Aを推奨する。** 過去の帳票を新システムで再生成する運用は想定しておらず（既存ファイルをそのまま `files` に移行する）、過去期間の設定解決でエラーが起きないことを優先する。

ただし移行後は、設定変更のたびに新しい有効期間の行が追加され、REQ-16 の要件が満たされる。移行時点より前の設定履歴は復元できないが、これは現行がその情報を保持していないためであり、受容せざるを得ない。

### 3.2 嚥下食区分の抽出（REQ-07, REQ-09）

現行に独立した嚥下食区分マスタが存在しない可能性が高い。献立種類（`menudisplay`）の名称に「ソフト食」「ミキサー食」「ゼリー食」が含まれる形と推定される。

**移行手順**

```
1. 献立種類マスタの全レコードを抽出
2. 名称から嚥下食区分を判定（ルールベース + 人手確認）
3. swallow_categories に3件を作成（sort_order = 1, 2, 3）
4. diet_types に嚥下食フラグと swallow_category_id を設定
5. menu_kinds を diet_types に紐付け
6. 判定できなかったレコードを一覧化して人手で対応
```

Step 2 の判定は自動化できない部分が残るため、**移行作業の中で最も人手を要する工程**になる見込み。実データの提供後に工数を見積る。

### 3.3 食種の特定（REQ-11, REQ-16）

食種マスタの所在が現行調査で特定できていない。以下の可能性がある。

| 可能性 | 確認方法 |
|--------|---------|
| 献立種類マスタに包含されている | 献立種類の値を確認 |
| Django Admin の未確認モデルに存在 | 全モデル一覧を確認 |
| コード上にハードコードされている | ソースコード確認（要提供） |
| 資料出力設定に埋め込まれている | 資料フォルダマスタの構造を確認 |

食種は REQ-11・REQ-16・REQ-17 のすべてに関わる中核マスタであり、**特定できるまで詳細な移行手順を確定できない**。

### 3.4 参照ロジックのフォールバック設定（REQ-21）

現行の361施設の参照ロジック設定を移行した上で、REQ-21 の要望に対応するフォールバック設定を追加する必要がある。

```
移行時: 現行の設定をそのまま移行（basic / lunch_only / contract_expired_zero 等）
移行後: 「基本パターン」に参照上限日数（例: 180日）とフォールバック先（直近実績）を設定
```

参照上限日数の妥当な値はクライアントとの協議事項。移行後の運用で調整できるよう、設定変更が即座に反映される設計とする（FR-704）。

### 3.5 ファイルの移行

献立資料・生成済み帳票のファイル実体を Cloud Storage へ移行する。

| 項目 | 対応 |
|------|------|
| 移行元 | `[要確認]` 現行のファイル格納場所（ローカルディスク / S3 等） |
| 移行方式 | `gsutil rsync` または Storage Transfer Service |
| メタデータ | `files` テーブルに登録し、`documents` / `report_files` と紐付け |
| スナップショット | 移行元に設定情報がないため、`settings_snapshot` は移行日時点の設定で埋める（`migrated: true` フラグを付与） |
| 検証 | 件数とチェックサムを照合 |

`settings_snapshot` に移行フラグを立てることで、移行データと新システムで生成したデータを区別できる。移行データについては「生成時点の設定が不明」であることを画面に明示する。

### 3.6 パスワードの再発行

現行は全ユーザーのパスワードがログインIDと同一（A-01）。移行時に以下を実施する。

| 対象 | 手順 |
|------|------|
| 社内ユーザー（6名） | 個別に初期パスワードを発行し、対面またはメールで通知。初回ログインで変更を強制 |
| 施設ユーザー（361施設） | 施設ごとに初期パスワードを発行し、書面またはメールで通知。初回ログインで変更を強制 |

361施設への通知は移行作業の中で最も調整を要する部分になる。切替の2週間前に通知を発送し、移行後に問い合わせが集中することを想定して社内の対応体制を準備する。

## 4. 移行手順

### 4.1 全体スケジュール（切替の前後）

| 時期 | 作業 |
|------|------|
| 切替2か月前 | 既存DBのスキーマ・データ提供を受ける。マッピング表を作成 |
| 切替6週間前 | 移行スクリプトを実装。**第1回リハーサル** |
| 切替4週間前 | データクレンジング。移行元データの不整合を現行システムで修正 |
| 切替3週間前 | **第2回リハーサル**。ステージングで受入テスト・性能テスト |
| 切替2週間前 | 施設への通知発送（初期パスワード・切替日時・操作マニュアル） |
| 切替2週間前 | 社内向け研修（2回） |
| 切替1週間前 | **第3回リハーサル（最終）**。切り戻し手順の確認 |
| 切替1週間前 | 切替判定会議 |
| 切替前日 | 現行システムへの入力を締切（アナウンス） |
| **切替当日** | §4.2 の手順 |
| 切替翌日〜1週間 | 集中サポート期間。問い合わせ対応体制を強化 |
| 切替1か月後 | 現行システムを参照専用に。1回目の請求サイクル完了を確認 |
| 切替3か月後 | 現行システムを停止 |

**切替タイミングの推奨。** 月初（1〜3日）の週末。理由は、前月分の請求処理を現行システムで完了させ、当月分を新システムで開始することで請求データの分断を避けられるためである。ただし正月・年度末は避ける。

### 4.2 切替当日の手順

```
【土曜 09:00】現行システムを停止（メンテナンス画面）
【土曜 09:30】現行DBのフルダンプを取得
【土曜 10:00】ダンプをGCPへ転送
【土曜 10:30】移行スクリプト実行（マスタ）
              → 件数照合
【土曜 13:00】移行スクリプト実行（トランザクション）
              → 件数照合・金額照合
【土曜 17:00】ファイル移行（Storage Transfer）
              → 件数・チェックサム照合
【日曜 09:00】検証（§4.3）
【日曜 15:00】切替判定
              ├─ Go   → DNS切替・新システム公開
              └─ NoGo → 切り戻し（§4.4）
【日曜 17:00】新システム公開
【月曜 08:00】社内サポート体制で業務開始
```

所要時間は既存データ量が不明なため概算である。第1回リハーサルで実測して確定させる。

### 4.3 移行後の検証項目

| # | 検証内容 | 判定基準 |
|---|---------|---------|
| 1 | マスタの件数照合 | 移行元と一致（意図的な除外を除く） |
| 2 | 施設・ユニットの件数 | 361施設 + ユニット数が一致 |
| 3 | 注文データの件数・合計食数 | 月別の合計食数が移行元と一致 |
| 4 | 請求データの金額合計 | 月別の請求金額が移行元と**完全一致** |
| 5 | ファイル件数・チェックサム | 全ファイルが一致 |
| 6 | 全ユーザーのログイン | 社内6名 + サンプル施設10件でログイン成功 |
| 7 | 週間注文入力の表示 | サンプル施設で行構成が正しく生成される |
| 8 | 発注スケジュールの表示 | 主要業者で表示され、発注量が移行元と一致 |
| 9 | 帳票生成 | 直近日分の主要帳票を生成し、移行元の出力と内容が一致 |
| 10 | 締切の解決 | 各注文種別で締切が正しく算出される |
| 11 | 参照ロジックの適用 | プレビューで361施設の解決結果が妥当 |
| 12 | 性能 | 発注スケジュール P95 3秒以内（NFR-01-4） |

**#4（請求金額の完全一致）を最重要の判定基準とする。** 金額の不一致は業務上許容できず、原因が特定できない場合は切り戻す。

### 4.4 切り戻し

| 項目 | 内容 |
|------|------|
| 判断期限 | 切替日曜 15:00（公開前） |
| 手順 | DNS を現行システムへ戻す。現行システムのメンテナンス画面を解除 |
| 所要時間 | 30分以内 |
| 公開後の切り戻し | 新システムで入力されたデータを現行へ戻す作業が必要になり困難。**公開後は切り戻さず、障害対応で解決する方針** |
| 前提 | 現行システムを切替後3か月間は稼働させたまま維持する |

公開後の切り戻しを想定しない代わりに、公開前の検証（§4.3）を十分に行い、リハーサルを3回実施する。

## 5. リハーサル

NFR-15-5 に基づき2回以上、本計画では3回実施する。

| 回 | 目的 | 検証内容 |
|----|------|---------|
| 第1回 | 移行スクリプトの動作確認 | エラーなく完走するか。所要時間の実測 |
| 第2回 | データ品質の確認 | §4.3 の全項目。不整合データの洗い出し |
| 第3回 | 本番手順の確認 | §4.2 の手順をタイムライン通りに実施。切り戻しも訓練 |

各回で発見した課題は移行元データのクレンジングまたはスクリプトの修正で解消し、次回で再検証する。

## 6. データクレンジング

移行元データに以下の不整合が想定される。移行前に現行システムで修正する。

| 想定される不整合 | 対応 |
|----------------|------|
| 契約終了日が未設定の終了済み施設 | REQ-20 の原因。現行で終了日を設定 |
| 商品マスタに紐付かない食材 | A-06。現行の10件を解消 |
| 重複した献立定型文 | REQ-18。移行前に整理するか、移行後に新機能で整理 |
| 掲載期間のないお知らせ（380件超） | A-10。移行時に一括で過去日を設定 |
| 参照ロジック未設定の施設 | 移行前に設定するか、既定値を適用 |
| ユニットの表示順が未設定 | 移行時に施設内の登録順で採番 |
| アレルギー設定の誤登録 | REQ-12。移行後に新機能で削除可能 |

「移行後に新機能で対応できるもの」と「移行前に修正が必要なもの」を切り分け、移行作業の負荷を抑える。

## 7. 並行運用期間の運用

切替後3か月間は現行システムを**参照専用**で維持する。

| 項目 | 内容 |
|------|------|
| 現行システムの状態 | 参照のみ。入力を禁止（アプリケーションレベルで書き込みを無効化） |
| 用途 | 移行データの照合、過去帳票の確認、問い合わせ対応 |
| アクセス権 | 社内ユーザーのみ。施設ユーザーのアクセスは切替時に停止 |
| 停止判断 | 3か月経過し、2回の月次請求サイクルが問題なく完了した時点 |
| 停止時 | 最終ダンプを取得して長期保管（`dan1-backups`） |

現行システムを完全な二重稼働（両方に入力）としない理由は、現場の二重入力負荷が過大であり、かつデータの不一致が発生した際にどちらが正しいか判断できなくなるためである。

## 8. 研修・移行支援

### 8.1 社内ユーザー（6名 → 20名）

| 回 | 対象 | 内容 | 時期 |
|----|------|------|------|
| 第1回 | 全員 | 全体像・画面構成の変更点・ログイン方法 | 切替2週間前 |
| 第2回 | 全員 | 業務別の操作演習（受注 / 発注 / 帳票 / 請求） | 切替1週間前 |
| 個別 | 管理者4名 | マスタ管理（締切・製造パターン・参照ロジック） | 切替1週間前 |

**マスタ管理の研修が最も重要である。** REQ-02 の要望「マスタでできないことが多いのでやりたい」に対して機能を提供しても、操作方法が伝わらなければ効果が出ない。§12の検証シナリオ（`06_master_management_spec.md` §12）を演習題材として使う。

### 8.2 施設ユーザー（361施設）

| 手段 | 内容 |
|------|------|
| 操作マニュアル | PDF を作成し送付。システム内からも参照可（現行も `/static/dan_order_manual.pdf` を提供） |
| 動画マニュアル | 週間注文入力の操作を録画（`[要確認]` 作成可否） |
| 切替案内 | 切替日時・初期パスワード・新URLを書面で通知 |
| 問い合わせ窓口 | 切替後1週間は電話対応を強化 |

361施設に個別研修を実施するのは現実的でないため、マニュアルと問い合わせ対応で吸収する。画面の操作性（REQ-04, 05, 06）が改善されていれば問い合わせは減るはずであり、この点も新システムの効果測定指標になる。

## 9. 移行の成功条件

| # | 条件 |
|---|------|
| 1 | 請求金額が移行元と完全一致する |

| 4 | 切替後最初の発注サイクルが完了する |

| 6 | 性能目標（NFR-01-4）を本番データで満たす |
