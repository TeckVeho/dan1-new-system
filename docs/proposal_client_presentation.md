## 現行システムの構造的課題

**2システム分離運用により、現場・社内双方に負荷が積み上がっています。**

| 課題 | 内容 |
|------|------|
| 運用が開発者依存 | 締切変更・嚥下食欄追加など、改善要望24項目中6項目が「マスタでできない」に起因 |
| 設定変更が過去データに遡及 | 食種変更で過去の献立資料まで内容が変わる |
| 同時作業ができない | 仕入業者単位ロック。1人が1業者を占有 |
| 性能・基盤の問題 | 発注画面が極端に遅い。週間注文は HTTP 500。在庫側は IP 直打ち・HTTP 平文 |

- 基幹: `order.dan1.jp`
- 在庫: `35.75.152.221`（HTTP）
- 仕入業者 23社／社内主利用者 約6名

## 新システムで目指す姿

| # | 目的 | 達成指標 |
|---|------|---------|
| 1 | 運用の自律化 | 開発者依頼が必要な設定変更をゼロに（現行6領域） |
| 2 | データ整合性 | 設定変更が過去帳票に遡及しない。生成時点の再現 |
| 3 | 同時作業性 | 業者を問わず複数人が同時に発注作業できる |
| 4 | 応答性能 | 発注スケジュール1週間分の表示を目標値内に |
| 5 | 業務のシステム内完結 | FAX・手作業（佐川・おせち・試食会）を取り込む |
| 6 | 基盤の統一 | 単一ドメイン・単一認証・HTTPS 化 |

**提案の核心:** 「画面をきれいにする」ではなく、設定駆動・スナップショット・非同期処理で運用そのものを変えます。

## システム全体像：As-Is → To-Be

### As-Is（現行）

- **施設（361件）** … 仮注文・食数変更・合数・アレルギー → 基幹へ
- **基幹 + 在庫（2系統）** … 手動取込・業者ロック・同期計算・ファイル出力
- **外部** … らくらく献立（Excel手動）／FAX／佐川（手動取込）

### To-Be（提案）

- **施設ポータル** … 週間注文（締切カウントダウン）・変更・特別注文・資料／請求閲覧
- **統合システム（単一ドメイン・HTTPS）** … 有効期間付きマスタ／楽観ロック／非同期ジョブ／帳票スナップショット
- **外部連携** … らくらく献立（非同期取込）／佐川 API／ラベルプリンタ・QR

## 主要な変更点

| 観点 | As-Is | To-Be |
|------|-------|-------|
| システム境界 | 2システム（別ドメイン・別UI） | 1システム（単一ドメイン） |
| 業者ロック | ログイン後に必須取得 | 廃止。レコード単位の楽観ロック |
| データ取込 | 手動・同期・1週間制限 | 非同期ジョブ・期間制限なし |
| 発注量計算 | 画面表示時に都度計算 | 取込完了時に事前計算・キャッシュ |
| 帳票 | 参照時に現在設定で描画 | 生成時点のスナップショットを保存 |
| 締切 | コード内固定（17:00）＋担当依頼 | マスタ設定＋例外日設定 |
| おせち容器 | FAX → 手作業転記 | 施設ポータルの特別注文枠 |
| 佐川伝票 | ファイル出力 → 手動取込 | API 連携 |

## 受注業務フロー（To-Be）

締切をマスタ化し、施設画面に残り時間を明示。  
未入力アラートは「注文義務のある施設」のみに限定。

| ステップ | 内容 |
|---------|------|
| 締切の可視化 | 「次回締切: 8/12(火) 17:00まで（残り 2日 4時間）」を全画面表示。例外日は社内マスタ登録 |
| 週間グリッド入力 | 列構成をマスタから動的生成。嚥下食追加もマスタだけで列が増える |
| 自動リマインド | 締切1時間前に未入力施設へ通知。契約終了・停止・長期休暇は除外 |

| 課題 | 解決方法 |
|------|---------|
| 週間入力が500エラー（REQ-04） | 週間グリッドUIを新規設計 |
| 締切が非表示・前倒しが手作業（REQ-13） | 締切ルール・例外日のマスタ化 |
| 終了施設がアラートに残る（REQ-20） | 注文義務判定ロジックで除外 |

## 発注・在庫業務フロー（To-Be）

業者ロックを廃止し、取込〜発注量計算を非同期化。  
画面は事前計算済みデータをページング表示。

| ステップ | 内容 |
|---------|------|
| ログイン | MFA。ダッシュボードで取込状況・不足を把握 |
| ファイル取込 | らくらく献立をまとめてアップロード → 非同期ジョブ |
| 自動計算 | 食数同期＋発注量を事前計算してキャッシュ |
| スケジュール確認 | 業者・納品日・商品絞込で高速表示（目標 P95 3秒） |
| 手動修正 | 楽観ロックで複数人同時編集。競合時は差分表示 |
| Excel出力 | 全件出力も非同期ジョブ化 |

**現場へのメリット:** 「ロック待ち」「1週間制限」「画面が重い」を同時に解消。

## 献立資料・帳票：版管理で整合性を担保

### As-Is の問題

施設マスタの食種設定が資料の**参照時**に結合 → 食種変更で過去資料まで変わる（REQ-16）。薄味混入（REQ-17）も同根。

### To-Be の設計方針

1. 設定に有効期間（valid_from / valid_to）を持たせる
2. 生成時の設定を `settings_snapshot` として保存
3. 参照時に現在マスタを再結合しない
4. 再生成は明示操作。旧版は保持
5. 食種変更は将来分の喫食日のみ影響

**配送・QR:** 製造パターン（D0〜D3）で集荷・着日算出。佐川は API（フォールバック CSV）。QR は本体と具材を別レコード化（REQ-15）。

## 請求業務フロー（To-Be）

発行済み請求書は不変。訂正は新バージョンとして記録。  
社内は施設画面の成り代わり閲覧が可能。

| ステップ | 内容 |
|---------|------|
| 締め | 対象月・施設を指定。単価・税率を有効期間で解決 |
| プレビュー | 施設別・合計を確認後、発行 |
| 公開 | 施設ポータルへ公開（現行のリンク未設定を解消） |
| 訂正 | 元データ保持。訂正レコード＋新バージョン発行と通知（REQ-03） |

成り代わり操作は監査ログに「代理操作」として記録。

## 新規にシステム化する業務

### おせち容器注文（REQ-19）

- 現行: FAX → 手作業転記
- 提案: 社内が特別注文枠（商品・受付期間・対象施設）を作成  
  → 受付期間中のみ施設ポータルに表示 → 集計から容器発注へ

### 試食会対応（REQ-24）

- 注文区分 `order_type=tasting` で連携先を制御
- **連携する:** 食数集計・調理表・計量表・盛付／ピッキング指示書
- **連携しない:** 佐川伝票・配送ラベル・請求・売価計算

## 業務カレンダー（喫食日基準の例）

例: **8/20 喫食分**（日数は現行画面からの推定。確定前に確認が必要）

| フェーズ | 期間（例） | 主なマイルストーン |
|---------|-----------|-------------------|
| 受注 | 8/5〜8/15 | 仮注文締切 8/12 → 変更締切 8/15 |
| 発注 | 8/13〜8/16 | 献立取込・自動計算 → 業者発注 8/16 |
| 製造・配送 | 8/18〜8/20 | 製造(D0)・集荷・着荷 → 喫食日 8/20 |
| 請求 | 翌月初 | 月次締め → 請求書発行 9/3頃 |

| 施設ユーザー | 社内（栄養士・事務） | 管理者・経営 |
|-------------|---------------------|-------------|
| 締切が画面で分かる | ロック待ちなく並行発注 | 設定変更の開発依存解消 |

| 資料・請求書をポータル閲覧 | 商品絞込・ビュー保存 | HTTPS・単一基盤 |
| 特別注文を FAX なしで完結 | 未入力催促の自動化 | 手作業・FAX の削減 |

| 目標 | 値 |
|------|-----|
| 開発者依頼の設定変更 | **0** |
| 発注スケジュール表示 | **P95 3秒** |
| 佐川伝票 | **API 自動化** |

## スコープ

### 対象範囲

| 領域 | 新システムでの扱い |
|------|------------------|
| 施設向け受注 | 統合。UI 全面刷新 |
| マスタメンテナンス | 統合。設定駆動へ再設計 |
| 社内業務（帳票・配送・請求） | 統合。カテゴリ再編 |
| 発注量計算・棚卸 | 統合。非同期化＋絞込 |
| Django Admin 直接編集 | 廃止。マスタ画面へ吸収 |

### 対象外

| 項目 | 理由 |
|------|------|
| らくらく献立本体 | 外部パッケージ。Excel 連携のみ |
| HACCP アプリ | 別システム |
| コーポレートサイト | 業務システムと無関係 |
| 会計システム | 連携先は要確認 |

**境界の確認事項:** QR 現行仕様、佐川 API 契約、売価計算の詳細範囲
